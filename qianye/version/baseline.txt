# 版本声明 —— 本 fork 全部「由人拍板」的版本号的唯一事实来源。
#
# 这里声明**两个互不相干**的版本号,不要把它们拼成一个:
#
#   内核版本  upstream_tag       我们同步到的上游 new-api 版本,格式与上游逐字一致。
#                               (2026-09-12 起它声明的是「同步到的口径」而非
#                                「逐字包含的全部内容」,详见下面 upstream_tag 那段。)
#                               它回答「这台机器上的内核是上游哪一版」。
#   二开版本  qy_version         我们自己的版本号,与上游的版本节奏无关。
#                               它回答「这台机器上跑的是我们的第几版」。
#
# 曾经有一版把两者合成 `v1.0.0-rc.25+qy.2` 一个字符串塞进 common.Version。
# 那是错的,而且错得很具体:
#   - 「系统维护 → 当前版本」于是既不是上游版本,也不是我们的版本;
#   - 上游那颗「检查更新」按钮拿它跟上游 release 的 tag_name 做**相等比较**,
#     带上 `+qy.2` 之后永远不相等,于是永远报「有新版本」,哪怕就是最新的;
#   - /api/status 的 version 与 X-New-Api-Version 是上游既有契约,外部脚本按
#     上游版本号的形状在读它,加后缀等于单方面改契约。
# 两个号各占一栏、各说各的事,上面三条同时消失。
#
# 为什么是一个手写的声明文件,而不是 `git describe` 算出来的:
#
# 本 fork 同步上游的方式是**逐提交挑拣**(取 blob / 三方合并 hunk),不是 merge。
# 挑拣不会把上游的 tag 变成 HEAD 的祖先,于是 `git describe --tags --abbrev=0`
# 报的是「HEAD 够得着的最近 tag」而不是「我们的代码同步到哪一版」。这两件事在
# merge 工作流下碰巧一致,在挑拣工作流下必然分叉,而且**分叉时不报错**:
# 2026-08-22 树里已经含有上游 v1.0.0-rc.25 的全部内容,describe 仍然报 v1.0.0-rc.24,
# /api/status 与 X-New-Api-Version 于是整整落后一个 release。
#
# 更根本的是:「我们到底同步到哪一版」带人的判断 —— 本轮就**故意不同步**
# e2c7aa7b1(前端测试迁 Vitest),理由记在 qianye/docs/upstream-provenance.md。
# 带判断的结论没有哪条 git 命令算得出来,只能声明。二开版本同理,而且更彻底:
# 「这一轮该进 MINOR 还是 PATCH」根本不是一个可计算的量。
#
# 【同步后 / 发版前必须改这里】改完跑 `go test ./qianye/version/...`:
# 形状不合法(tag 不是 vX.Y.Z 形态、describe 与 tag 对不上、二开版本不是
# vX.Y.Z、或还停在 v0.0.0)会直接红。文件被删或改名则 go:embed 让**编译失败**,
# 而不是悄悄退回 unknown。

# ───────────────────────────── 二开版本(我们自己) ─────────────────────────

# 二开版本号。语义化版本,恒为 vMAJOR.MINOR.PATCH,不带预发布段、不带 build
# metadata —— 因为它**必须能比大小**(检查更新要判断「远端那个是不是更新」),
# 而预发布段与 build metadata 的比较规则是 semver 里最容易被实现错的一段。
#
# 递增规则(人工,发版时改,与 upstream_tag 各改各的):
#   MAJOR  二开自己的对外契约破坏性变更:/api/qy 接口删字段或改语义、
#          qianye-prod.yaml 的配置键不兼容、扩展库迁移不可回退。
#   MINOR  新增功能面(新模块、新页面、新接口),向后兼容。
#   PATCH  只修缺陷,不加功能面。
# 同步一次上游**不**自动进位:那件事记在 upstream_tag / upstream_describe 里。
#
# 为什么不用 `git describe` 或 commit 数自动生成:
#   - `git describe` 的输出(v1.0.0-rc.24-109-g1228d77e8)是从**上游的 tag**
#     算出来的,上游一打新 tag 它就整体跳变,它描述的根本不是我们的版本;
#   - commit 数单调但没有语义,而且**每一次提交都会变** —— 检查更新会因此在
#     一个从未发布过的中间提交上报「有新版本」;
#   - 这两种都不能表达「这一版破坏了兼容性」,而那正是版本号存在的理由。
#
# 【发版流程】改这一行 → 提交 → 在 fork 仓库打 tag `qy-<本值>`(例 qy-v0.1.0)
# → 在该 tag 上建一个 GitHub Release。检查更新读的就是这个 Release
# (见 qianye/controller/update_check.go)。tag 刻意带 `qy-` 前缀:上游的
# tag 名字全是 `v*`,一旦有人把 upstream 的 tag 推进 fork,不带前缀的两套
# tag 会混在同一个命名空间里,检查更新会把上游的 release 当成我们的。
#
# 【递增记录】只记「进了哪一位、为什么」,一行一版,不复述改了什么 ——
# 改了什么由 git log 与 Release 正文负责,这里只负责那个**判断**。
#   v0.1.0  起始值。取 0.x 而不是 v1.0.0:0.x 是「还没做出稳定性承诺」的
#           通行写法,而这个 fork 此刻确实没有。
#   v0.2.0  MINOR。两轮新增功能面,全部向后兼容:双色球一次买多注(注数
#           可配到 999)、建活动向导给推荐值、竞猜改成看得懂的彩池盘口、
#           大厅三玩法分 Tab。
#           **最接近 MAJOR 的一条是 common.MaxQuota 的上界抬高,判定为不进
#           MAJOR**:MAJOR 的三条触发项是「/api/qy 删字段或改语义」「配置键
#           不兼容」「扩展库迁移不可回退」,抬高一个上界一条都不占 ——
#           字段还在、语义没变(仍然是「全站额度换算的整数上界」)、没有配置
#           键、没有迁移。而且方向是**放宽**:此前每一个合法取值现在仍然
#           合法,此前能过的调用现在没有一个会被拒。破坏性变更的判据是
#           「原先能用的现在不能用了」,放宽上界永远不满足它。
#
#           【升级注意 —— 唯一一处「原先合法、现在被拒」】
#           lottery.max_total_entries_hard 新增硬顶 524288(= 2^19)。它此前
#           **没有任何上界**,只校验 > 0,所以一份把它配成 60 万的 YAML 在
#           v0.1.0 上能正常启动,在 v0.2.0 上会 FATAL 退出(不是降级,是拒绝
#           启动),错误里会点名字段、收到值与上界。
#           为什么仍判 MINOR 而不是 MAJOR:MAJOR 的触发项写的是「配置**键**
#           不兼容」——键还在、语义没变、类型没变,变的是取值区间的一端,
#           而且默认值 50000 与示例配置都在新上界的十分之一以下,不存在
#           「默认配置起不来」。这一条按「升级注意」记,不按破坏性变更记。
#           收紧它的理由:它与 common.MaxQuota 是同一条溢出防线的两个因子
#           (`hit * p.AmountQuota` 是资金路径上最大的一处裸 int64 乘法),
#           抬高任何一边都会把那条防线拆掉,所以两边都必须有硬顶。

#   v1.0.0  **MAJOR**。lottery.prize_secret_key 由「可留空」变成「必填」:开着
#           娱乐功能却没配这把钥匙的部署,升级之后**拒绝启动**(FATAL,不是降级)。
#           这一条正中 MAJOR 的第二项触发器 ——「qianye-prod.yaml 的配置键不兼容」:
#           一份在 v0.2.0 上能干净启动的 YAML,在 v1.0.0 上起不来。
#
#           为什么值得进 MAJOR 而不是继续兼容:留空的语义是**明文直存**。
#           qy_lot_payout.secret_cipher 存的是发给中奖者的实际兑换码,与提现的
#           收款账号、AI 渠道的 api_key 同级,而后两者从第一天起就是密文。
#           列名叫 cipher、内容却是明文,意味着库备份 / 只读报表账号 / 离线 dump
#           三条路上兑换码全部裸奔,而在线侧那一整套控制(不下发、只回掩码、
#           reveal 强制事由 + 双写审计)对它们一条都不起作用。
#           一次一次性的运维动作(生成 32 字节随机数)换掉一个默认不安全的形状。
#
#           【升级步骤】lottery.enabled 为 true 的部署,升级前先在 YAML 里填上
#             prize_secret_key: "<openssl rand -base64 32 的输出>"
#           不想现在处理就把 lottery.enabled 置 false,功能整块关闭即可正常启动。
#           启动失败时的报错会点名这个键并给出上面两条出路。
#
#           【不丢数据】升级前已履行的兑换码不会失效:它们以 key_version=0 记在
#           行上,读路径照旧(openPrizeSecret 按行上的版本号选路径),并由启动后
#           的一次性回填就地转成密文(qianye/modules/lottery/prize_secret_backfill.go,
#           先封装再解回来逐字节比对通过才写库,CAS 恒为 version=0,只前进不后退)。
#
#           **为什么是 v1.0.0 而不是 v0.3.0**:上面的递增规则没有为 0.x 写例外,
#           破坏性变更就进 MAJOR。0.x 的「还没做出稳定性承诺」是对**用法**说的,
#           不是一个把破坏性变更藏进 MINOR 的许可 —— 那样运维在版本号上永远看不到
#           「这一版会让我起不来」。
#
#           【同一版里的另外两件事,都不单独构成 MAJOR】
#
#           ① 分组限流的口径从**模型分组**纠正回**用户分组**。
#           上游那段代码是「令牌分组优先、用户分组兜底」,在上游成立是因为
#           users.group 同时兼作模型分组;本 fork 把两者拆开之后,它塌成了
#           「模型分组优先」,而页面文案写的一直是 "for a specific user group"。
#           表现:运营在限流页填的用户分组名永远查不到,那一行静默失效;
#           auto 令牌更是全站共用 ModelRequestRateLimitGroup["auto"] 一个桶。
#           不进 MAJOR 的判据:**升级前配好的键仍然生效**(查不到用户分组时
#           回落到原来那个键再查一次),没有任何一份现存配置会因为升级而失效。
#
#           ② 新增「按用户分组的在途并发上限」(option 键
#           ModelRequestConcurrencyGroup,默认空 = 全站不限)。纯新增功能面,
#           不写这个键时行为与升级前逐位一致。**它按节点计数**,多节点部署下
#           配 N 的实际效果是「每节点 N」,这句话在配置页的提示文案里写死。
#
#           同批还有一条**收紧**但不单独构成 MAJOR 的校验:
#           lottery.prize_secret_keys_retired 不再允许包含当前启用的版本号
#           (withdraw.pii_keys_retired 早有这道检查)。它拦的是一次做了一半的轮换:
#           旧钥搬进了退役表却忘了抬 prize_secret_key_version,于是同一个版本号下
#           新密文用新钥、历史密文用旧钥,后者永久不可读且没有任何迹象。
