# design-16 · 风控预警(可疑用户监听取证)

## 0. 一句话

管理员对某个用户 / 某个分组 / 某个分组的某个模型立一个**监听任务**,设定记录概率、
抽取条数、抽取时间,系统按这个口径把命中请求的上下文原样留档,供事后翻看。
**只观察不处置**,记录写进一个**单独配置的存储节点**。

---

## 1. 它与违规检测不是一件事

| | 违规检测(design-07) | 风控预警(本文) |
|---|---|---|
| 回答的问题 | 这一条内容违不违规 | 这个账号最近到底在做什么 |
| 谁发起 | 全站自动,按规则 | 管理员**指名立案** |
| 处置 | 拦截 / 扣费 / 封号 | **无**。只留档 |
| 判据 | 词表、正则、频率、AI 审核 | 作用域 + 概率,没有"判据"可言 |
| 数据去向 | 主扩展库(+ 可选台账库) | **必选的独立存储节点** |

它存在的理由只有一条:**一个刚被举报的账号,规则库里没有任何一条能命中他,
而"他到底在问什么"在此之前没有任何地方查得到。** 查到之后的处置仍然走既有的路
(违规规则、封号策略、工单),这一页只负责让人看得到该处置谁。

## 2. 为什么强制一个单独的存储节点

监听记录存的是被抽中请求的**完整上下文**(归一化后的整段提示词),而抽多少、抽多久
由运营在管理端**临时**决定 —— 一个「永久监听 + 100% 概率」的任务,一天就能写进
几十 GB。这个量既不由代码决定,也不由部署时的配置决定,而是由某个管理员下午三点
点的那一下决定。

把它放进任何一个已有的库都会得到同一个结局:某次监管操作把磁盘写满,而跟它一起
躺下的是佣金账本、两阶段资金单,或者整个网关的日志表。

所以:

- `risk_watch.database.dsn` **必填**。`risk_watch.enabled: true` 而 dsn 为空
  **直接拒绝启动**(`validateRiskWatch`),不静默禁用 —— 静默禁用会让"忘了配存储
  节点"表现成"功能开着但一条都不抓",而那是本仓最不愿再遇到的失效形状。
- `db.Watch()` 在没配时返回 **nil,不回落主库**。回落会让漏配表现成"功能正常,
  数据默默写进了主库",而那正是这一段配置存在的全部理由要防的事。
- 两张表都住在那个库里,**不与主库或台账库 JOIN**、不参与任何跨库事务
  (`module.WatchTabler` 的硬约束)。

它与台账库(design-00 / `log_database`)的零值方向**相反**:那一个留空 = 跟着主库走,
这一个留空 = 整个功能不注册。连接、熔断、健康探测这些机制两者共用一份
(`qianye/db/secondary.go`),差异全部留在包装函数里。

## 3. 表

两张,都在存储节点上。

### 3.1 `qy_riskwatch_task` — 监听任务

作用域是**三格的组合**,不是三种类型:`target_user_id` / `user_group` / `model_name`,
零值 = 不限。项目方点名的三种形态(某个用户 / 某个分组 / 某个分组的某个模型)
都是这三格的取值,"某个用户的某个模型"这种一望即知的第四种形态也顺带成立。

**三格全空会被接口拒绝**(`qy_rw_scope_empty`)。它在这里不是"全站监听"而是一个陷阱:
一个全站 100% 的任务在列表页上与一个用户级任务长得一模一样。

| 格 | 含义 | 零值 |
|---|---|---|
| `sample_bps` | 记录概率,万分比(10000 = 100%) | 必填 > 0 |
| `max_records` | 抽满多少条自动停止 | 0 = 不限 |
| `captured` | 已抓条数。**它是闸门本身**,不是统计值 | — |
| `window_mode` | forever / range / countdown,只决定回显 | — |
| `starts_at` / `ends_at` | 判定只认这两个时间戳 | 0 = 立即 / 永久 |
| `retention_days` | `*int`:nil = 跟全局默认,0 = 永久保留,N = N 天 | 三个语义值 |
| `status` | running / stopped / finished / expired | — |
| `stopped_reason` | manual / max_records / window_end / group_deleted | — |
| `version` | 乐观锁 | — |

`retention_days` 用指针是因为它有**三个**语义值而 int 只能表达两个 ——
"没填"与"填了 0"在业务上完全不同,而本仓在 `commission.holding_days` 上栽过一次
同形状的跟头。

### 3.2 `qy_riskwatch_capture` — 监听记录

一行 = 一次被抽中的请求。带 `task_id` 归属、用户 / 密钥 / 分组 / 模型 / IP /
`request_id`、归一化后的 `content`、多模态附件的**描述符**(MIME / 字节数 / SHA256,
不含二进制本体),以及 `expires_at`。

索引:`(task_id, created_at)`、`(user_id, created_at)`、`(expires_at)`。
列表的排序键因此是 `created_at desc, id desc` 而不是单纯 `id desc` ——
PostgreSQL 的二级索引不隐含主键(InnoDB 隐含),只按 `task_id` 建索引的话,
一个抓了几十万条的任务翻第一页也要先把全部命中行取出来再排一次。

## 4. 热路径

挂在 `qianye/relayguard` 的**观察者**一侧。

### 4.1 为什么要有 relayguard

上游 `controller/relay.go` 里那一行 `service.QyPreRelayGuard` 是一个**单槽变量**。
违规检测当年直接 `service.QyPreRelayGuard = PreRelayGuard`,那在只有一个消费方时
没有问题;第二个消费方出现的那一刻就变成**静默互斥** —— 后赋值的把前一个整个顶掉,
而编译、单测、启动日志全部正常,唯一的表现是其中一个功能线上零命中。
`model.QyOnConsumeLog` 上已经记过同一笔(lottery 绕开它靠的是"自己扫库",
这里绕不开:要的正是热路径上那一刻的提示词文本)。

于是把插槽收进 `qianye/relayguard`:模块登记,分发器持有,**上游那一行一个字都不改**。

### 4.2 观察者排在闸门之前

```
Observer(只观察,永不拦截)  →  Gate(可以拒绝,第一个报错即中止)
```

反过来会让**被拦下来的那一次请求完全不进观察**,而那恰恰是风控最想看到的一条:
一个账号连续撞违规词、每次都被拒,监听记录里却一条都没有。

自调用断路器(AI 审核把 base_url 误填成本站时)也在分发器里,整条放过 ——
那一次请求的内容属于**别人**,记进持有 key 的账号名下比不记要坏得多。

### 4.3 一次命中的完整顺序

```
maybeRefresh()          内存快照,到期才异步重载(snapshot_seconds)
snapshot.tasks 为空     → 返回
作用域闸(纯内存比较)   → 不在作用域内一次骰子都不摇
抽样(crypto/rand)      → 每个任务各摇各的
db.WatchAvailable()     → 存储节点不可用即放弃这一批
snapshotRow()           → 从 gin.Context / RelayInfo 上**抄下来**(异步侧稍后才用)
guard.HotAsync × N      → 每个命中的任务各写一行
```

作用域闸必须排在抽样**之前**:反过来会让界面上那个"10%"变成"作用域内的 10% 乘以
一个谁也说不出来的数",而记录概率是这个功能唯一的成本闸门,它必须是字面意思。
抽样又排在**取文本**之前 —— 取文本要重建整段 `CombineText`,是这条路径上最贵的一步。

### 4.4 抓的是转发**之前**那一刻

记录里只有用户发过去的上下文,**不含模型回复**。回复要在转发之后才存在,而流式
响应是边转发边吐的,要留档就得在热路径上边转发边聚合整段输出 —— 那是给主业务加
内存与延迟,而取证要看的九成是"他问了什么"。

## 5. 「抽满 N 条自动停止」怎么兑现

这是这个功能唯一一条"运营在页面上写下的承诺",它只能靠一条带条件的原子 UPDATE 兑现:

```sql
UPDATE qy_riskwatch_task SET captured = captured + 1
WHERE id = ? AND status = 'running' AND (max_records = 0 OR captured < max_records)
```

`RowsAffected = 0` 就是"没抢到",此时这一条**不落库**,并把任务改成 `finished`。

预留与插入在**同一个事务**里(两张表都在这个存储节点上,是本地事务)。先 COUNT
再 INSERT 的写法在多节点(甚至单节点多 worker)下必然超抓,而超抓的表现是
"我明明设了 500 条,库里有 623 条" —— 一个没人能解释、也没办法回滚的数字。

内存快照里的 `captured` 只用来让一个明显已满的任务提前退出,**不是闸门**。

## 6. 清理与状态可见性

两个后台任务,都跑在扩展库的租约保护下(`lease.Run`,租约表在**主库**;
这是本模块唯一一处同时依赖两个库的地方,而租约是"谁来跑"的协调、不是业务数据):

| 任务 | 周期 | 做什么 |
|---|---|---|
| `riskwatch.prune` | `gc_interval_minutes`(60) | 按 `expires_at` 分批删过期记录 |
| `riskwatch.sweep` | 1 分钟 | 把窗口已过的 running 任务改成 `expired` |

保留期在**落库那一刻**折算成绝对时间戳(`expires_at`),让清理成为一条带索引的
范围删除;改任务保留期时由管理端接口一次性重写这一列(`rewriteExpiry`),
那是一次有边界的、管理员触发的操作。

`sweep` 解决的是**状态可见性**,不是"让任务停止抓取" —— 后者由内存快照按本节点
时钟判定,是立即的。没有它,一个零流量站点上昨天到期的任务会在管理端一直显示
"运行中",而管理员据此以为还在抓。

删除任务会**连带删掉它的全部记录**,且不放进一个事务:一次删除可能涉及上百万行,
包进事务会在这个正在被热路径写入的库上持有一个巨大的 undo。中途失败留下的是
"任务还在、记录少了一批",下一次点删除会继续 —— 反过来才是查不清的那种残留。

## 7. 上下文清洗:与违规检测**刻意不同**的一条策略

落库前三件事:剥离内联二进制 → 抹掉凭证 → 按 `capture_max_chars` 掐头去尾截断。
顺序不可换:先截的话一张 base64 图片能把整条记录占满,正文一个字都没留下。

违规检测的脱敏还会抹掉邮箱、手机号、身份证、银行卡。**这里不抹。**

理由是场景相反:那一套服务于**全站自动归档**(管理员研判一条自动命中的违规,
不需要知道用户的手机号,而平台留着它就要承担个人数据的全部责任);这里是一次由
管理员**指名立案**的定向取证,而个人标识符常常就是证据本身 —— 批量生成诈骗短信、
往一串手机号里灌营销文案、拿别人的身份证号编材料,把这些抹掉之后留下的记录恰好
证明不了任何东西。

凭证是唯一的例外,而且方向相反:一把被用户粘进提示词的 API key 对研判毫无价值,
却会让这个取证库变成一个凭证仓库。所以它照抹。

**这不是"同一份口径的第二份实现",是两条不同的策略。** 做成一个可配的通用脱敏器
是错的:那会让"抹不抹手机号"变成一个开关,而它其实是这两个功能各自定义的一部分。

## 8. 分组改名 / 删除

`qy_riskwatch_task.user_group` 是**判据**,`qy_riskwatch_capture.user_group` 是**证据**。
两者性质相反,处置必须分开(`residue.go`):

- **改名** → 任务那一列跟着改,记录那一列一个字不动(改它就是篡改证据)。
- **删除** → 把命中的**运行中**任务**停掉**,分组名原样保留。

摘空在这里是**放宽**:三格作用域里空串 = 不限,摘掉 `user_group` 之后,一个原本只盯
vip 分组的任务会变成盯全站;要是它本来就只填了这一格,摘完就是一个全站任务。
停掉是 fail-closed,留名字让这份立案记录事后还读得懂。

已知偏差:`ResidueHandler` 的契约要求 `Sweep` 使用传入的 `tx`,而本模块的表在另一个
数据库上,**做不到**。显式接受的代价是"主事务回滚 + 已经扫过 → 几个任务被多停了
一次",管理员点「启动」即可恢复;不扫的代价是"一条指向已删分组的监听任务静默存活,
将来同名分组被重新创建时突然对一批毫不相干的新用户生效"。后者才是不可接受的那个。

## 9. 配置

```yaml
risk_watch:
  enabled: false
  database:              # 必填,与 log_database 同规格(MySQL / PostgreSQL)
    dsn: "..."
  snapshot_seconds: 30   # 任务快照刷新周期
  max_active_tasks: 50   # 同时运行的任务上限,0 = 不限
  capture_max_chars: 4000
  retention_days: 30     # 任务没填保留期时的默认值,0 = 永久
  max_retention_days: 365
  gc_interval_minutes: 60
  gc_batch_size: 2000
```

出厂 `enabled: false`。这个功能会把用户的原始请求内容留档,不该由一次二进制升级
替站点决定。

## 10. 管理端

`/qy/admin/risk-watch`(「风控与审计」组,紧跟 AI 审核日志)。九条路由,全部 AdminAuth。
**没有用户端路由** —— 被监听的人不该知道自己在被监听。

每个写接口各有**恰好两处**审计(成功一条、失败一条):这个功能的产出是别人的原始
请求内容,谁在什么时候开始盯谁、盯了多久、用多大概率,本身就是必须可被审计的事实。

删除是唯一挂 `CriticalRateLimit` 的那一条 —— 它销毁的是不可逆的取证材料。

## 12. 三库验证

存储节点与主库、台账库共用 `qianye/db` 的整套迁移、锁与方言分支,因此三把迁移锁
必须**各不同名**(MySQL 的 `GET_LOCK` 是服务器实例级的,而最常见的部署恰恰是
"同一台 MySQL 上三个 schema")。

已在真实 MySQL 8.0.28 与 PostgreSQL 16.4 上跑过:

- `TestExtensionAutoMigrateIsIdempotent` —— 首次迁移 + 第二次零 DDL,两种方言
- `TestRiskWatchMigratesOnItsOwnHandle` —— 表建在存储节点里、不在主库里;
  主库表不跑到存储节点;第二次迁移不退化成降级态
- `TestExtensionSchemaHasNoFixedWidthCharColumns` —— 无定长 CHAR 列
